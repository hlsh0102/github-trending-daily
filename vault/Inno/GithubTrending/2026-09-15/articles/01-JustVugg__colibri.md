## 项目概述

Colibrì（仓库名 `JustVugg/colibri`）是一个用纯 C 编写的 MoE（Mixture-of-Experts，混合专家）大模型推理引擎。它要解决的问题很具体：前沿 MoE 模型的参数规模已经从数百 B 增长到数 T，常规做法要求把全部权重放进显存或内存，普通用户几乎无法承担。Colibrì 的思路是不再追求“把模型装进设备”，而是把**存储、内存和显存视为一个统一的推理层级**（AI memory multitiering），专家权重按需从磁盘流式加载，从而在消费级与异构硬件上运行 744B 至 2.8T 参数的模型。

项目的目标用户包括：只有单机或几块消费级显卡、但希望本地运行大模型的个人开发者；需要在异构硬件（不同 GPU、不同内存容量）上部署推理的研究者；以及关注 MoE 推理调度、分层缓存策略的工程人员。引擎本身不含第三方运行时依赖，编译产物是一个体量很小的 C 可执行文件。

## 核心功能

- **超大 MoE 模型推理**：当前支持九个模型家族，包括 GLM-5.2/5.3（744B）、GLM-5.3-Flash（321B，带视觉）、Inkling（975B）、Kimi K3（2.8T）、DeepSeek V4 Flash（284B）、DeepSeek V4.1 Flash（552B，带视觉）、Qwen3.8-Flash-Next（125B + 51B n-gram）、Qwen3.6（35B-A3B）与 OLMoE（7B）。
- **AI 内存多级分层**：将磁盘、RAM 和 VRAM 组织成统一的推理层级，专家权重按访问模式在层级间流动，避免一次性加载全部参数。
- **磁盘专家流式加载**：专家块直接从磁盘读取并按需参与计算，显著降低对内存与显存容量的硬性要求。
- **统一前端命令**：无论运行哪个模型家族，都使用同一套 `coli chat`、`coli serve`、`coli web` 接口，分别对应交互式对话、API 服务和 Web 界面。
- **纯 C 零依赖**：整个引擎以 C 实现，不引入额外的引擎依赖，便于在受限环境和老旧工具链上构建。
- **每模型单文件适配**：各模型家族对应一个 C 文件，新增模型时的改动范围相对可控。

## 技术架构

Colibrì 的核心设计是把推理过程拆解为“计算”与“权重供给”两条路径。计算路径只关心当前 token 需要激活哪些专家；权重供给路径负责把这些专家的参数从最慢但容量最大的存储层搬运到最快的计算层。这种设计直接对应 MoE 的稀疏激活特性——每次前向只需少量专家，因此磁盘带宽和缓存命中率成为关键指标，而非总参数量。

分层结构上，磁盘承担全量专家权重的持久化，RAM 作为中间缓存，VRAM 承载当前参与计算的张量。引擎需要在三者之间做预取、淘汰与复用决策，以隐藏 I/O 延迟。由于不依赖 BLAS 之外的框架，算子实现和调度逻辑都在 C 层完成，减少了运行时开销与部署复杂度。

从工程组织看，每个模型家族一个 C 文件意味着模型差异被隔离在适配层，共享的分层调度、采样与服务框架保持不变。这也解释了为什么 `coli chat`、`coli serve`、`coli web` 能在所有模型间通用。

## 安装与使用

项目提供 GitHub Releases 发布页，同时需要按目标模型准备权重文件。一般流程如下：

1. 从 Releases 页面获取最新的构建产物，或在本地使用 C 编译器从源码构建。
2. 下载所选用模型家族对应的权重，并按文档要求放置在指定目录，确保磁盘空间足够容纳完整专家权重。
3. 根据硬件配置设置分层参数，例如可用于缓存的 RAM 上限、可用的 VRAM 容量与磁盘权重路径。

最小可用示例（以交互式对话为例）：

```
coli chat --model <model-name> --weights <path-to-weights>
```

如需以服务方式对外提供接口，使用 `coli serve`；如需浏览器交互界面，使用 `coli web`。具体参数名与可用选项请以仓库文档和 `--help` 输出为准。

## 适用场景

- **单机本地运行超大 MoE 模型**：硬件配置有限，但希望通过磁盘流式加载运行 744B 乃至 2.8T 级别模型。
- **异构硬件部署**：机器上混合了不同型号显卡与不同容量内存，需要统一调度存储、RAM 与 VRAM。
- **MoE 推理研究与实验**：研究专家激活模式、缓存命中率、预取策略对吞吐和延迟的影响。
- **低依赖环境的模型服务**：需要在无额外运行时框架的纯 C 环境中提供 `serve` 或 `web` 接口。

## 项目亮点

与常见的“量化后塞进显存”路线不同，Colibrì 的差异点在于把存储纳入推理层级，而不是把存储当作临时交换区。这一取向让它在参数量远超本地内存时仍然可用，且无需对模型做激进的精度压缩。

其次是零依赖的纯 C 实现。相比依赖 Python 栈或特定推理框架的方案，它的部署面更窄、构建更直接，适合嵌入到已有 C/C++ 工程或受限运行环境中。

第三是模型覆盖的广度与统一接口的组合：九个模型家族、从 7B 到 2.8T 的跨度，共用同一套命令，降低了在不同模型间切换的迁移成本。项目采用 Apache-2.0 许可，允许商业使用与修改。

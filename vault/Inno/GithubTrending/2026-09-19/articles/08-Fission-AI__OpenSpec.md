## 项目概述

OpenSpec 是一个面向 AI 编程助手的规范驱动开发（Spec-Driven Development，SDD）框架，由 Fission-AI 开源并以 MIT 协议发布。它解决的核心问题是：当开发者借助 AI 助手（如 Claude Code、Cursor 等）编写代码时，需求与实现之间往往缺乏明确、可追溯的约定。AI 助手容易在缺乏约束的情况下自由发挥，导致代码偏离预期、难以审查，也不利于多人协作。

OpenSpec 通过在人类开发者与 AI 助手之间引入一层结构化、可版本化的规范文件，把“想做什么”与“怎么做”显式分离。目标用户包括使用 AI 辅助编码的个人开发者、需要在团队内规范 AI 工作流的工程团队，以及希望在既有代码库（brownfield）中逐步引入 AI 协作的组织。其设计哲学强调流动而非僵化、迭代而非瀑布、简单而非复杂，并能从个人项目扩展到企业级使用。

## 核心功能

- **规范驱动的开发流程**：以结构化规范文件作为需求与实现的中间层，AI 助手基于规范生成代码，保证输出可预期、可审查。
- **工件引导工作流（Artifact-Guided Workflow）**：新版工作流围绕规范工件组织任务，通过 `/opsx:propose` 等命令引导用户从提议到实现的完整链路。
- **AI 助手集成**：与主流 AI 编程助手协同工作，作为其行为约束和上下文来源，而非替代助手本身。
- **面向既有代码库**：支持在已有项目中渐进式引入规范，而非要求从零重写或全新启动。
- **迭代式协作**：允许规范随需求演进持续更新，契合敏捷与迭代开发节奏。
- **命令行工具**：通过 npm 分发的 CLI（`@fission-ai/openspec`）提供初始化、规范管理等操作。

## 技术架构

项目以 TypeScript 为主要开发语言，通过 npm 包 `@fission-ai/openspec` 对外分发，可运行于 Node.js 环境。整体采用命令行工具（CLI）形态，便于集成到开发者的日常终端工作流及 CI 流程中。

架构上的关键设计在于“规范即工件”的分层思路：规范文件与代码分离存放，作为独立、可版本控制的资产。AI 助手读取规范而非直接读取模糊的自然语言需求，从而降低歧义。工作流引擎负责串联“提议—确认—实现—迭代”各阶段，使每一步都有明确的输入与产出。仓库通过 GitHub Actions 提供持续集成，保证工具本身的稳定性。这种设计让 OpenSpec 更像是一个轻量的流程协调层，而非重量级的建模或代码生成系统。

## 安装与使用

OpenSpec 通过 npm 分发，安装方式通常如下（需预先安装 Node.js）：

```bash
npm install -g @fission-ai/openspec
```

在项目根目录初始化后，即可生成规范目录结构：

```bash
openspec init
```

随后在 AI 助手的会话中，通过内置命令（如 `/opsx:propose`）发起规范提议，助手会依据规范工件展开实现工作。最小的可用流程是：编写或生成一条规范 → 让 AI 助手基于该规范产出代码 → 根据结果迭代更新规范。具体命令与参数以官方文档为准，上述为基于常见用法的概述。

## 适用场景

- **AI 辅助的日常编码**：为 AI 助手提供明确边界，减少反复澄清与返工。
- **团队协作与代码评审**：规范文件可作为评审依据，让 AI 生成的改动更易被理解和追溯。
- **在旧项目中引入 AI**：无需重写既有系统，可对局部模块逐步建立规范。
- **需求与实现的可追溯管理**：规范演进的版本历史本身就是一份需求变更记录。

## 项目亮点

与直接向 AI 助手描述需求，或使用重量级建模工具相比，OpenSpec 的差异点在于“轻量且流动”。它不追求一次成型的完整规格，而是允许规范与代码交替迭代，贴近真实开发节奏；同时明确面向 brownfield 场景，承认大多数工作发生在既有代码之上。其规范文件采用纯文本形式、便于版本控制，且对具体 AI 助手保持一定中立性。配合活跃的社区（Discord 与持续的 CI），项目在个人项目到企业规模之间具备较好的伸缩性。

## 项目概述

Colibrì（仓库名 `JustVugg/colibri`）是一个用纯 C 编写的 MoE（Mixture of Experts，混合专家）大模型推理引擎。它要解决的问题很具体：前沿级 MoE 模型的参数量已经达到 744B 至 2.8T，常规做法要求把全部权重装入显存或内存，普通用户几乎无法负担。Colibrì 的思路是把存储、内存（RAM）和显存（VRAM）视为一个统一的分层推理体系，专家权重按需从磁盘流式加载，从而在消费级与异构硬件上运行这些模型。

引擎本身零第三方依赖，每个模型家族对应一个 C 文件，共用同一套 `coli chat` / `coli serve` / `coli web` 前端。目标用户是希望在本地自有硬件上跑大模型的研究者、工程师和爱好者，以及对推理引擎内部实现感兴趣、愿意阅读和修改 C 代码的开发者。

## 核心功能

- **AI 内存分层（AI memory multitiering）**：将磁盘、RAM、VRAM 组合为单一推理层级，专家权重按访问需求在层间流动，而非要求全量常驻。
- **超大 MoE 模型支持**：已适配九个模型家族，包括 GLM-5.2/5.3（744B）、GLM-5.3-Flash（321B，含视觉）、Inkling（975B）、Kimi K3（2.8T）、DeepSeek V4 Flash（284B）、DeepSeek V4.1 Flash（552B，含视觉）、Qwen3.8-Flash-Next（125B + 51B n-gram）、Qwen3.6（35B-A3B）和 OLMoE（7B）。
- **统一前端**：无论底层是哪个模型，交互入口保持一致，提供对话、服务端和 Web 三种使用方式。
- **零引擎依赖**：纯 C 实现，不引入外部运行时或框架，便于审计、交叉编译与嵌入。
- **异构硬件利用**：同时调度磁盘 I/O、系统内存与 GPU 显存，适配显存容量不一的设备组合。

## 技术架构

核心设计是分层内存管理。传统推理引擎假设权重常驻某一级存储，Colibrì 则把专家权重的驻留位置当作可调度资源：高频专家留在 VRAM 或 RAM，低频专家留在磁盘，推理时按路由结果拉取。这要求引擎在 I/O 预取、缓存淘汰与计算流水线之间做配合，避免磁盘读取成为串行瓶颈。

实现层面，项目以“一个模型一个 C 文件”的方式组织，模型定义与引擎核心解耦，新增模型家族不需要改动通用推理逻辑。引擎不依赖 BLAS、CUDA runtime 之外的第三方库，量化与算子实现自带。这种取舍牺牲了一部分通用性，换来的是可移植性和可读性——整个推理路径都在可审计的 C 代码中。

## 安装与使用

项目为 C 语言工程，通常的构建路径是先克隆仓库、按平台准备编译器与可选的 GPU 工具链，再执行构建脚本生成 `coli` 可执行文件。具体命令与依赖清单请以仓库 README 和 releases 页面为准。

最小可用示例（示意，实际参数以文档为准）：

```bash
git clone https://github.com/JustVugg/colibri
cd colibri
# 按 README 指引构建
./coli chat --model <模型名或权重路径>
```

下载对应模型权重后，通过 `coli chat` 进入交互对话，`coli serve` 启动兼容 API 的服务端，`coli web` 打开浏览器界面。首次运行会因磁盘流式加载而较慢，缓存预热后延迟下降。

## 适用场景

- **消费级硬件上运行大 MoE 模型**：显存和内存不足以容纳全量权重时，通过磁盘流式加载仍可推理。
- **异构设备整合**：手头有不同代际 GPU、大小不一的显存和 SSD 存储，希望统一利用而非闲置。
- **推理引擎研究与教学**：代码量可控、无外部依赖，适合分析 MoE 路由、量化与内存调度的实现细节。
- **本地私有化部署**：不依赖云服务，权重与推理过程留在本机。

## 项目亮点

与常见的 llama.cpp 等本地推理项目相比，Colibrì 的差异点在于目标模型规模量级和内存模型假设。它不追求在单一设备上塞进模型，而是明确把磁盘当作推理层级的一部分，从而支撑 744B 乃至 2.8T 级别的 MoE。纯 C、零依赖、一模型一文件的组织方式，也使它在可移植性和可审计性上区别于依赖大量第三方库的推理框架。Apache-2.0 许可证允许商业与衍生使用。
